# DrawFlow Demo Interaction Specification

## 0. Purpose

This document is the executable implementation specification for the DrawFlow Core Build Workspace demo slice.

The demo must not be a static UI mock. It must be a functional product slice backed by live Convex demo tables and demo functions. Every visible interactive control in the demo must either:

1. mutate explicit persisted demo state through a named Convex mutation/action,
2. open a drawer/modal that exposes further executable controls,
3. trigger a deterministic derived-state recomputation, or
4. be deliberately marked out of scope and visually disabled with a clear reason.

A visible enabled control with no handler, no domain mutation, no event, and no test coverage is a defect.

## 1. Round 1 Locked Decisions

### 1.1 Demo Objective

The demo must prove all of the following:

- UI/product vision.
- Workflow correctness.
- Agent implementation quality.
- Investor/customer demo credibility.

Workflow correctness wins over visual polish. The product should still look polished, dense, and credible, but visual fidelity does not count unless interactions are executable.

### 1.2 Product Shape

The demo is a single cohesive product slice, not a sandbox of unrelated widgets.

The demo is a full interactive sandbox for the in-scope slice. It should feel like a perfect mirror of the intended production system for the scoped interactions, not a lightweight prototype.

### 1.3 Persistence and Runtime Architecture

Major requirement change:

- Zustand is removed from the demo architecture.
- Live Convex tables and functions are required.
- Every demo table must use a `demo_` prefix.
- Every demo function must use a `demo_` prefix.
- The demo must include a seed script.
- The demo must include a cleanup/reset script.
- The demo must be restartable from a fresh canonical state.

Implementation implication:

- Convex is the authoritative state store.
- React component-local state is allowed only for ephemeral UI state such as open drawers, currently dragged item, selected tab, temporary form draft before submit, or local validation presentation.
- Domain truth must not live only in React state.
- Domain truth must not be hardcoded into component arrays except as seed-data constants used by the seed script.

### 1.4 Demo Modes

The demo includes two isolated modes:

1. Proposal Builder mode.
2. Active Build Workspace mode.

They are isolated from each other for demo purposes.

Proposal Builder mode:

- Fully executable for the scoped proposal interactions.
- Ends at pressing Submit Proposal.
- Proposal approval/activation interface is out of scope.
- The active build does not need to be generated by approving the proposal in this demo.

Active Build Workspace mode:

- Pre-seeded as an already active build.
- Focuses on active-build interaction patterns.
- Must support completion claim, evidence, review, site visit, admin approval, automatic draw release approval, rollover buffer, audit, and event outbox behaviors.

Demo scenario switching:

- A demo can expose a clearly labeled scenario switcher between Proposal Builder and Active Build Workspace.
- The two scenarios are isolated. Mutating the proposal scenario must not mutate the active-build seed unless explicitly implemented as a resettable demo handoff, which is currently out of scope.

### 1.5 Proposal Mode Scope

Proposal mode must support:

- Add milestone.
- Reorder milestones.
- Edit milestone estimated/approved-value candidate.
- Edit estimated duration.
- Drag planned dates on the Gantt.
- Add dependency.
- Remove dependency.
- Mark dependency as hard or soft.
- Move milestone between draw groups.
- Split draw group.
- Merge draw group.
- View deterministic planning impact.
- Compare draw-plan recommendations.
- Submit proposal.

Proposal submission is terminal for this demo. No approval UI is required.

### 1.6 Active Build Scope

Active-build mode must support:

- View approved baseline.
- View active forecast/actual reality.
- Open milestone detail.
- Update progress.
- Update forecast dates with required reason/comment.
- Upload completion proof.
- Add sample evidence for deterministic tests.
- Submit completion claim.
- Request lower draw amount.
- View rollover-buffer state.
- Review evidence.
- Request more information.
- Request site visit.
- Complete site visit.
- Submit site visit report.
- Approve milestone completion as lender admin.
- Automatically mark draw group release-approved once all included milestones are completion-approved.
- Record audit events.
- Record event outbox entries.

Active-build mode must not support:

- Editing approved dependencies.
- Editing approved draw group membership.
- Editing approved baseline values.
- Proposal approval.
- Manual release recording.
- MIC/read-only observer projection.

Active-build Gantt dragging:

- Must be supported.
- Must update forecast dates only.
- Must preserve approved baseline dates.
- Must require a reason/comment.
- Must record an audit event.

### 1.7 Roles

No real auth is required for the internal demo.

However, the UI must represent the following role perspectives or permission modes:

- Builder Lead.
- Lender Admin.
- Site Visitor.

Out of scope:

- Builder Staff.
- Lender Staff as a separate role.
- MIC Observer.
- Demo Admin role.

Because there is no auth, role switching is a demo control, not a security boundary. It should be visually clear that this is a demo role/persona selector.

### 1.8 Site Visitor Experience

The Site Visitor experience is not a full separate app.

It must be a focused responsive flow reachable from the active-build workspace, likely through a drawer, modal, or dedicated panel. It must be sufficient to execute the site visit interaction pattern end-to-end.

### 1.9 Release Workflow Scope

Completion approval and draw release approval are simplified for the demo:

- Milestone completion approval is explicit and performed by Lender Admin.
- Draw release approval is automatic after all milestones in the draw group are completion-approved.
- Manual release recording is out of scope.
- Funds movement is out of scope.
- The UI must not imply that money has been sent.

### 1.10 Evidence and Upload Scope

Evidence upload must support both:

- Real browser file input, storing file metadata in Convex demo tables.
- Add Sample Evidence actions for deterministic Playwright tests.

Completion proof is required for every completion claim.

Cost evidence is not required.

### 1.11 Planning Engine and Cost Calculations

The demo must include a deterministic planning engine.

It must not be random, AI-generated, or precomputed-only static output.

The planning engine must enforce and flag invariants, including construction-sequencing invariants not explicitly present in the original PRD, such as:

- Roofing cannot be completed before framing.
- Framing is a hard blocker for downstream work where construction logic requires it.
- Hard construction blockers cannot be bypassed without visible warning/override semantics.

The planning engine should feel like a JIT compiler for the build plan:

- It continuously surfaces errors and warnings as the user creates invalid states.
- It must not silently fix the user's plan without an explicit user action.
- It distinguishes blocking errors from non-blocking warnings.
- Blocking errors prevent proposal submission or completion claim submission.
- Soft warnings can remain visible while still allowing submission.

Cost calculations must be real enough to recompute from current state:

- Changing a draw schedule must affect total estimated financing cost.
- Changing draw groups must affect total estimated financing cost.
- Changing release/eligibility timing assumptions must affect total estimated financing cost.
- Draw fees must be computed separately.
- Interest must be computed, not hardcoded.
- The bottom/status region must show running/total cost and breakdown.

### 1.12 Audit and Event Outbox

Audit events must be visible in the UI.

Webhook/network delivery is out of scope, but an event outbox/log must be shown. Event outbox entries should be deterministic records of what would be published.

### 1.13 Explicitly Cut From Demo

The following are out of scope for this demo slice:

- Proposal approval interface.
- Active-build creation from proposal approval.
- Manual release recording.
- MIC Observer role.
- Read-only MIC/API projection panel.
- Real auth / WorkOS integration.
- Payment execution.
- Ledger/accounting truth.
- Native mobile app.
- Offline sync.
- Geofencing.
- Cost-evidence reimbursement workflow.
- Builder receipt/double-confirmation workflow.

### 1.14 Forbidden Implementation Shortcuts

- No enabled dummy buttons.
- No enabled dummy drag handles.
- No enabled interactions that only show `Coming soon`.
- No fake affordances that look interactive but have no handler.
- No domain state stored only in component-local state.
- No static hardcoded state after seed, except for immutable display constants.
- No rendering-only Playwright tests counted as coverage.
- No Playwright tests with generic titles like `renders workspace` as primary verification.
- Every Playwright test title must map to a user flow or interaction contract.
- The final implementation report must include a coverage matrix mapping every visible control to command/function and test.

## 2. Canonical Seed Build

### 2.1 Project Type

The canonical seed build is a large single-family full-build construction project.

### 2.2 Working Capital Constraint

The starting maximum borrower working capital exposure is locked at CAD $260,000.

Each draw group's approved value must be less than or equal to CAD $260,000.

Any milestone outside the currently active/reachable draw group is blocked by unavailable capital unless earlier reimbursement has made that draw group reachable.

### 2.3 Milestone Modeling Rule

Every legible budget row is a milestone.

There is no concept of a `non-Gantt budget row` in this demo. This is intentional because:

- Builders will use rows like permits, reserves, management fees, materials, utilities, and soft-cost-like items as part of draw grouping.
- Later iterations will support custom milestone creation.
- Real builder-entered schedules are messy.
- The system must handle that messiness rather than pretending all rows are clean physical construction tasks.

All included rows appear as milestone cards and Gantt rows.

The only omitted row is the unlabeled `$10,000.00` row because it is non-legible.

## 3. Round 2 Locked Decisions: Domain Logic

### 3.1 Dependency Storage

Dependencies must be explicitly stored as graph edges in `demo_milestoneDependencies`.

### 3.2 Dependency Types

Use the following dependency types:

- `hard_blocker`
- `soft_dependency`
- `procurement_dependency`

### 3.3 Hard Blocker Semantics

Hard blockers behave as follows:

- They do not prevent dragging a schedule into an invalid state.
- They immediately create visible validation errors/warnings.
- They prevent proposal submission while unresolved.
- They prevent completion claim submission while unresolved.
- Lender Admin override is out of scope for this demo unless explicitly reintroduced.

### 3.4 Soft Dependency Semantics

Soft dependencies behave as follows:

- They create warnings, not blocking errors.
- They do not prevent proposal submission.
- They should still be visible in the validation panel and milestone drawer.

### 3.5 Procurement Dependency Semantics

Procurement dependencies behave as follows:

- They indicate a material/procurement milestone should be complete or sufficiently progressed before corresponding install work is complete-claim eligible.
- They may be blocking or warning-level depending on the specific edge configuration.
- Default demo behavior: procurement dependencies block completion claim submission for the dependent install milestone.

### 3.7 Example Invariant: Roofing Before Framing

The UI may allow an invalid draft schedule in Proposal Builder where roofing is visually dragged before framing.

However:

- The invalid schedule must be immediately flagged.
- The invalid state must prevent proposal submission.
- Roofing completion must be impossible before framing completion in Active Build.

### 3.8 Working Capital Semantics

Max working capital means each draw group approved value must be `<= $260,000`.

Current unreimbursed exposure includes all completed, submitted, approved-but-not-release-approved work not yet reimbursed.

Because manual release recording is cut from the demo, `release_approved` is treated as reimbursed for working-capital purposes.

Milestones outside the active/reachable draw group must show a capital-blocked reason.

Capital block must appear as a distinct blocking reason from dependency block.

A milestone can show multiple blocking reasons at the same time.

### 3.9 Draw Group Recompute Semantics

Proposal Builder:

- Draw groups can be recomputed.
- Recompute should happen when the user clicks `Recompute Plan`, chooses an optimizer scenario, or explicitly asks the engine to apply a recommendation.
- Recompute should not silently happen on every keystroke.

Active Build:

- Draw group membership is frozen.
- Active build draw groups never recompute membership.
- Only statuses, forecast dates, rollover buffer, cost estimates, and eligibility recompute.

## 4. Cost, Fee, and Interest Model

### 4.1 Cost Model Goal

The layout optimizer exists partly to minimize financing cost under working-capital constraints.

The optimizer must weigh:

- Maximum working capital exposure.
- Interest exposure from earlier draws and longer outstanding periods.
- Flat per-draw fees.
- Number of draw groups.
- Timing of draw eligibility/release approval.
- Draw size.
- Dependency feasibility.
- Whether milestones can run in parallel.

### 4.2 Interest Rate

Default pending unless overridden later:

- 12.00% annual nominal.
- Daily compounding.
- Actual/365.

### 4.3 Draw Fee

Draw fee is a flat CAD $500 per draw group with a non-zero requested draw amount.

There is exactly one CAD $500 fee per draw group that actually requests capital.

If a draw group has `$0` requested amount, no CAD $500 draw fee is incurred because no capital draw occurred.

The fee is not a percentage of draw value.

The fee is not capitalized unless later explicitly changed.

Formula:

```ts
drawFees = count(drawGroups where requestedDrawAmount > 0) * 500
```

### 4.4 Interest Start Date

Because manual release recording is out of scope, estimated interest starts the day after automatic release approval date.

### 4.5 Payoff / Takeout Date

Default pending unless overridden later:

- User can edit assumed payoff/takeout date in Proposal Builder.
- Payoff/takeout date is read-only in Active Build.
- Seed payoff horizon is 12 months after first draw release.

### 4.6 Bottom Cost Summary

The bottom/status region must show a deterministic cost summary that separates:

- Approved project value.
- Projected capital actually drawn.
- Requested draw value for the selected/active draw group.
- Remaining approved budget.
- Rollover buffer / unclaimed budget buffer.
- Flat draw fees.
- Estimated interest.
- Total estimated financing cost.
- Total projected borrower cost.

Projected borrower cost should be shown as:

```ts
projectedBorrowerCost = approvedProjectValue + flatDrawFees + estimatedInterest
```

The UI must also show that projected capital actually drawn may be lower than approved project value because borrowers are not forced to draw unused/under-budget capital.

Important: reserves, management fee, permits, and similar rows are still milestones and part of approved project value.

### 4.7 Recalculation Rules

Changing Gantt forecast dates in Active Build must recompute interest estimates because draw eligibility/release timing shifts.

Changing draw groups in Proposal Builder must recompute:

- Number of draw fees.
- Draw timing.
- Interest exposure.
- Capital-blocked/reachable status.
- Total estimated financing cost.

## 5. Rollover Buffer Model

### 5.1 Scope

Rollover buffer is active-build only.

It must not exist in Proposal Builder because rollover is created when real-world work comes in under budget.

### 5.2 Creation

Each lower draw request creates a milestone-level rollover buffer record.

Example:

- Milestone approved value: 2% of total budget.
- Builder requests only 1% because work came in under budget or they do not need all capital.
- The remaining 1% becomes available budget buffer.

### 5.3 Allowed Use

Rollover buffer is available across all other milestones and draw groups.

It must never allow the project to be overfunded.

It must never allow a future draw to exceed total approved remaining project value.

### 5.4 Cost Impact

Unclaimed budget buffer reduces interest exposure because the borrower is not forced to draw all available capital.

Therefore rollover buffer can reduce total projected cost.

It changes cash-flow timing and interest exposure, not the original approved construction value.

### 5.5 Zero-Dollar Draw Requests

The builder may request `$0` for a completed milestone, creating a full rollover buffer for that milestone's approved value.

A zero-dollar draw request does not incur the flat CAD $500 draw fee because no capital draw occurred.

### 5.6 Max-Cash-On-Hand / Capital Shock Guardrail

The demo must include a max-cash-on-hand guardrail to prevent unsafe capital shocks.

Use this rule:

```ts
maxCashOnHand = min(260_000, remainingApprovedProjectValue * 0.30)
```

Applying rollover to a future draw is allowed only when:

```ts
requestedDrawAmount + currentUnspentCashOnHand <= maxCashOnHand
```

If applying rollover would violate this guardrail:

- The UI must show a capital shock warning.
- The action must be blocked.
- The failed attempt should be visible to the user.

## 14. Round 4 Locked Decisions: Active Workspace Interaction Model

### 14.1 Route and Shell

Routes:

- `/demo/drawflow/active`
- `/demo/drawflow/proposal`

The active workspace is the default landing route.

Scenario switching is route-based, not tab-based:

- The Proposal control is a link to `/demo/drawflow/proposal`.
- The Active control is a link to `/demo/drawflow/active`.
- Proposal and Active scenarios remain isolated demo states.

The active workspace top bar must include:

- Reset Demo.
- Audit.
- Event Outbox.

Persona switching may reload the page if that yields cleaner implementation. Immediate client-side switching is not required. The UI must still reflect the selected persona deterministically after the switch.

Disabled controls must explain missing permission or blocked state. Example: `Only Lender Admin can approve milestone completion.`

### 14.2 Naming Convention: Milestone-Cards vs Rail-Cards

Use these terms consistently:

- `milestone-card`: the card in the vertical milestone rail/list on the far left.
- `rail-card`: the Gantt/timeline bar/card representing a milestone on the chart.

Do not call the Gantt bars `milestone cards` in implementation comments, tests, or specs. That ambiguity caused prior implementation drift.

### 14.3 Active Workspace Selection Behavior

Clicking a `milestone-card` must:

- Set the milestone as actively selected.
- Scroll/pan the Gantt timeline horizontally to bring the corresponding `rail-card` into view.
- Scroll/pan the Gantt vertically if needed to bring the corresponding row into view.
- Highlight the selected milestone-card.
- Highlight the selected rail-card.
- Highlight milestones that block the selected milestone using one color/visual treatment.
- Highlight milestones blocked by the selected milestone using a second color/visual treatment.
- Open the Milestone Detail Sheet.

The detail sheet must not blur, darken, or visually obscure the workspace. The workspace must remain visible for spatial context while the sheet is open.

Clicking a `rail-card` must:

- Set the milestone as actively selected.
- Show vertical date runners/indicators at that milestone's current start date and end date.
- Open or sync the Milestone Detail Sheet for that milestone.

### 14.4 Active Gantt Controls

The Gantt must include a single-select time resolution control with these options:

- Days
- Weeks
- Months

The implementation may render this as a segmented control, select, toggle group, or compact button group. Only one resolution is active at a time.

The Gantt must include a size slider that changes the width of time columns without changing the selected time resolution.

Examples:

- Resolution = Months, column size = compact.
- Resolution = Months, column size = wide.
- Resolution = Weeks, column size = wide.

Changing column size must not mutate domain state. It is view state only.

Changing time resolution must not mutate domain state. It is view state only.

### 14.5 Active Gantt Layout and Responsiveness

The Gantt chart must take the full available width. It must not cut off the right side because of fixed sizing or parent overflow mistakes.

The Gantt chart area is scrollable horizontally and vertically as needed.

The vertical milestone rail on the far left is collapsible.

When the milestone rail is collapsed:

- The Gantt expands to use the freed width.
- The current scroll position and selected milestone should be preserved where feasible.
- The collapsed state is view state only.

Responsiveness/scaling requirements:

- The layout must remain usable at typical laptop widths.
- The Gantt canvas must avoid hard-coded widths that clip content.
- Time columns scale based on container width, selected resolution, and size slider.
- Draw group boxes and rail-cards must use the same coordinate system.

### 14.6 Draw Group Box Geometry

Draw group boxes must enclose every row in that draw group.

For each draw group bounding box:

- Left edge = earliest start date among milestones in the draw group.
- Right edge = latest end date among milestones in the draw group.
- Top edge = top of the first row occupied by a milestone in the draw group.
- Bottom edge = bottom of the last row occupied by a milestone in the draw group.

The box must not only wrap the top row. It must cover the vertical span from the top-left of the earliest milestone row to the bottom-right of the latest milestone row.

Draw group labels must not overlap rail-cards. If insufficient space exists inside the box, the label should move to an outer header position, use an offset, or use a compact chip with tooltip.

### 14.7 Draw Group Cascading / Capital-Constrained Sequencing

Draw groups are sequentially capital-constrained.

In Active Build, when a milestone forecast change extends the end date of a draw group:

- The draw group end date extends.
- Later draw groups' earliest start dates are pushed back as needed.
- The next draw group cannot begin until one day after the previous draw group is eligible/release-approved/reimbursed for demo purposes.
- For the demo, use this simplified clamp: `nextDrawGroupStartDate >= previousDrawGroupEndDate + 1 day`.
- Cascading must update Gantt rail-card positions for affected future draw groups.
- Cascading must update cost/interest estimates.
- Cascading must write the initiating forecast-change audit event and may write derived recomputation metadata.

When a milestone forecast change reduces the end date of a draw group:

- The draw group end date contracts.
- The next draw group's start date auto-clamps earlier if it was only delayed by the prior draw group end.
- Use the same simplified clamp: `nextDrawGroupStartDate = max(originalDependencyStartDate, previousDrawGroupEndDate + 1 day)`.
- Later draw groups may move earlier if no dependency or capital rule prevents it.
- Cost/interest estimates recompute.

This behavior applies to forecast scheduling in Active Build and planned scheduling in Proposal Builder, but Active Build mutates forecast dates only and never mutates approved baseline dates.

### 14.8 Active Gantt Dragging

Active Build Gantt shows both:

- Approved baseline bar.
- Current forecast/actual foreground bar.

Dragging in Active Build must mutate forecast dates only. Approved baseline dates are immutable.

Dragging a rail-card edge must display the drag handle only on hover/focus. Drag handles must not appear if the corresponding drag behavior is not implemented.

Active drag flow:

1. User drags the forecast rail-card or one of its resize handles.
2. UI previews new forecast position/dates.
3. System opens a reason modal before persistence.
4. User enters reason.
5. User confirms.
6. Convex mutation persists forecast dates.
7. Derived validation recomputes.
8. Draw group geometry recomputes.
9. Capital-constrained cascading recomputes future draw group starts.
10. Cost summary recomputes.
11. Audit event is written.
12. Event outbox entry is written where appropriate.

Cancelling the reason modal reverts the rail-card to its prior forecast dates.

Dragging into hard dependency violation is allowed, but the persisted forecast must immediately show `forecast_invalid` and block completion claim submission until corrected.

Invalid forecast does not block progress updates.

## 17. Round 5 Locked Decisions: Proposal Builder Interaction Model

### 17.1 Route and Shell

Proposal route:

- `/demo/drawflow/proposal`

Proposal Builder top bar must include:

- Active Build link.
- Proposal Builder current-route indicator.
- Reset Demo.
- Analyze Plan.
- Apply Recommended Plan.
- Submit Proposal.
- Time Resolution: Days / Weeks / Months.
- Column Size Slider.

Proposal Builder top bar must not include primary Audit and Event Outbox controls.

Audit and Event Outbox controls belong in the Proposal Builder footer / bottom status region. The footer may expose compact audit/outbox buttons, latest event counters, or expandable panels, but they are not top-bar actions in Proposal Builder.

Proposal Builder does not need persona switching. It is a builder/planner workspace. Persona and permission nuance belongs primarily in Active Build.

### 17.2 Proposal Setup Drawer

Proposal Builder includes a `Proposal setup` drawer/control.

The setup drawer exposes:

- Working capital cap: CAD $260,000.
- Annual interest rate.
- Payoff/takeout date.
- Flat draw fee: CAD $500.
- Project start date.
- Planning mode: capital-constrained sequencing.

Changing proposal setup values triggers just-in-time recalculation after state changes, not a purely manual Analyze Plan requirement.

### 17.3 Just-In-Time Proposal Analysis

Proposal Builder must behave like a JIT compiler for the plan.

When proposal state changes:

- Mark current derived analysis as stale/pending.
- Display a small loading spinner or analyzing indicator.
- Start a debounce timer of 2–3 seconds.
- Reset the timer on every subsequent state change.
- Only after the user stops interacting for the debounce interval should the recalculation actually run.
- The recalculation updates visible warnings/errors, current cost summary, draw group status, capital utilization, and submit readiness.

This JIT recalculation is distinct from explicit `Analyze Plan`:

- JIT recalculation keeps the current draft projection current.
- `Analyze Plan` creates a formal deterministic planning run with recommended order, recommended grouping, diff, and applyable recommendation.

### 17.4 Proposal Seed State

Proposal Builder loads with all 44 cleaned legible milestones.

Proposal Builder starts in the builder-provided messy row order.

Proposal Builder starts with naive draw groups computed from the builder-provided row order under the CAD $260,000 cap.

Proposal Builder starts as editable draft:

```ts
proposal.status = "draft"
```

Hard dependency warnings/errors should become visible after the initial JIT analysis completes. The initial analysis should show the small loading spinner first, then surface the errors/warnings.

Submit Proposal is disabled at initial load because the builder-provided draft has hard dependency/order conflicts.

### 17.5 Proposal Milestone-Cards

Clicking a Proposal Builder `milestone-card` follows the same spatial selection model as Active Build:

- Select milestone.
- Scroll Gantt to corresponding `rail-card`.
- Highlight selected milestone-card.
- Highlight selected rail-card.
- Highlight blockers and blocked-by milestones using distinct visual treatments.
- Open the detail sheet.
- Do not blur/darken the workspace.

Proposal milestone-cards are vertically reorderable.

Reordering milestone-cards mutates:

- `milestone.proposalSortOrder`.
- `milestone.updatedAt`.

Reordering milestone-cards does not automatically rewrite draft planned dates. It triggers debounced JIT analysis so ordering warnings/errors and summary projections can update.

Milestone-card drag handles are visible only if reorder behavior is implemented.

Milestone-card up/down buttons are required as accessible alternatives to drag/drop.

### 17.6 Proposal Rail-Cards

Proposal `rail-cards` support:

- Drag body to move milestone start/end together.
- Resize left edge to change start date.
- Resize right edge to change end date.
- Click to select and show date runners.

Rail-card edge drag handles are visible on hovering/focusing that edge.

Proposal rail-card dragging/resizing persists immediately. There is no reason modal in Proposal Builder.

If drag/resize creates a hard dependency violation:

- Persist the draft mutation.
- Surface blocking error/warning via JIT analysis.
- Keep Submit Proposal blocked.

If drag/resize creates a draw group over CAD $260,000:

- Persist the date mutation.
- Surface draw group cap error as blocking plan error.
- Keep Submit Proposal blocked.

Proposal Gantt dragging updates current draft cost summary through JIT recalculation. Formal optimizer recommendations still require `Analyze Plan`.

### 17.7 Proposal Detail Sheet

Proposal milestone detail sheet exposes:

- Name.
- Approved/proposed value.
- Duration.
- Draft planned start date.
- Draft planned end date.
- Draw group.
- Dependency editor.
- Blocking / blocked-by list.
- Warning/error list.
- Delete milestone.
- Duplicate milestone.

Users can edit milestone name.

Users can edit milestone value. If the value causes the draw group total to exceed CAD $260,000, the system persists the edit but surfaces a blocking draw-cap error.

Users can edit duration directly. Editing duration changes draft end date based on current draft start date.

Deleting a milestone is allowed:

- Custom-created milestones may be deleted.
- Seeded milestones require confirmation.
- Seeded milestones are soft-deleted / excluded, not hard removed.

Duplicate milestone is included. It creates a new custom milestone seeded from the selected milestone, then selects the duplicate and opens its detail sheet.

### 17.8 Add Milestone

Add Milestone button lives in the left milestone rail header.

Adding a milestone creates:

```ts
name = "New Milestone"
approvedValue = 0
durationDays = 1
draftPlannedStartDate = dayAfterLatestMilestoneEnd
draftPlannedEndDate = same day
drawGroupId = lastDrawGroupId
status = "draft"
isCustom = true
```

Newly added milestone is immediately selected and opened in the detail sheet.

Adding a milestone writes an audit event.

Adding a milestone does not need to write an outbox event because no external proposal event exists until submission.

A zero-value milestone blocks proposal submission and surfaces a validation error such as `missing_value`.

### 17.9 Dependency Editor

Dependency editor allows adding dependencies via searchable milestone picker.

Dependency edge types:

```ts
type DemoDependencyType =
  | "hard_blocker"
  | "soft_dependency"
  | "procurement_dependency";
```

Adding a cycle is prevented. Cycles are structurally invalid and must not be persisted.

Changing dependency type recomputes warnings/errors via debounced JIT analysis.

Removing dependencies:

- User-created dependencies may be removed.
- Dependencies involving user-created/custom milestones may be removed.
- Pre-existing/system hard dependencies on seeded milestones cannot be fully removed.
- System hard dependency removal controls must be disabled with explanation.
- System hard dependencies should be visually distinguishable from user-created dependencies.

Removing a removable hard dependency immediately clears related warnings if no longer applicable after JIT analysis.

### 17.10 Analyze Plan

Analyze Plan runs the deterministic planning engine.

Analyze Plan produces:

- Hard dependency errors.
- Soft warnings.
- Cycle errors.
- Draw group cap errors.
- Milestone ordering issues.
- Unreachable/capital-blocked sequence issues.
- Financing cost estimate.
- Draw fee estimate.
- Interest estimate.
- Recommended order.
- Recommended draw grouping.
- Recommendation diff from current plan.

Analyze Plan does not mutate the proposal. It creates a `demo_planningRuns` recommendation record that the user may explicitly apply.

Analyze Plan writes an audit event.

Analyze Plan does not write an event outbox entry.

### 17.11 Apply Recommended Plan

Apply Recommended Plan requires confirmation.

Apply Recommended Plan mutates:

- Milestone proposal sort order.
- Draft planned dates.
- Draw group membership.
- Draw group planned start/end.
- Proposal warning/error state.
- Cost summary.
- Planning run applied status.

Apply Recommended Plan preserves manually edited milestone names and values.

Apply Recommended Plan preserves custom milestones and places them according to dependencies, dates, and capital constraints.

Apply Recommended Plan writes an audit event.

Apply Recommended Plan is disabled if there is no fresh planning run.

### 17.12 Submit Proposal

Submit Proposal requires:

- No hard dependency errors.
- No cycles.
- No draw group over CAD $260,000.
- All legible milestones included or explicitly soft-deleted/excluded with confirmation.
- No zero-value milestones.
- No missing durations.
- No invalid dates.
- JIT analysis is fresh.
- If a formal Analyze Plan is required by the current validation state, the latest planning run must be fresh.

Submit Proposal transitions:

```ts
proposal.status = "submitted"
```

After submission, Proposal Builder becomes read-only.

Submitted proposal shows terminal banner:

```txt

```

Submit Proposal writes audit event and event outbox entry:

```ts

```

### 17.13 Proposal Draw Group Behavior

Proposal draw boxes use the same geometry rule as Active Build:

- Left edge = earliest milestone start in the draw group.
- Right edge = latest milestone end in the draw group.
- Top edge = first row occupied by a milestone in the draw group.
- Bottom edge = last row occupied by a milestone in the draw group.

Moving a milestone into another draw group should support both drag/drop and detail-sheet control if feasible. Minimum required implementation is the detail-sheet draw group dropdown.

Draw group total updates immediately when membership or milestone value changes.

Draw group over CAD $260,000 is a blocking error.

Users can manually split and merge draw groups.

Split/merge updates:

- Flat draw fee count.
- Interest estimate.
- Financing cost estimate.
- Draw group geometry.
- Submit readiness.

### 17.14 Proposal Capital-Constrained Cascading

Extending a draw group pushes later draw groups back.

Rule:

```ts
nextDrawGroupStartDate >= previousDrawGroupEndDate + 1 day
```

Reducing a draw group pulls later draw groups earlier where possible.

Cascading happens immediately after drag/resize date mutations, with visible rail-card movement. JIT analysis may then update warnings/cost/error state after the debounce interval.

Optimizer recommendations still require Analyze Plan.

## 20. Round 6 Locked Decisions: Convex Schema, Functions, and Seed Contract

This section defines the Convex implementation contract. Coding agents must implement this directly unless they find an impossible conflict with the existing repo conventions, in which case they must stop and document the conflict instead of inventing a parallel architecture.

### 20.1 Convex Naming Rules

All public Convex functions for this demo must start with `demo_`.

All Convex demo tables must start with `demo_`.

Internal TypeScript helpers may use normal names and should not be exported as public Convex functions unless needed.

Do not use Zustand for domain truth.

Do not store demo domain state only in React component state.

React state is allowed only for ephemeral view state:

- Selected milestone ID.
- Open/closed drawer state.
- Current time resolution.
- Column size slider value.
- Current persona selector.
- Pending drag preview before confirmation.
- Temporary form input before submit.

### 20.2 Canonical Demo IDs

Use deterministic string identifiers for seeded demo records wherever possible. Convex document `_id` values will still be generated by Convex, but every seeded domain entity must also include a deterministic `demoKey`.

Required scenario keys:

```ts
type DemoScenarioKey = "proposal" | "active";
```

Required tenant/build keys:

```ts
const DEMO_TENANT_ID = "demo_tenant_drawflow_internal";
const DEMO_PROJECT_KEY = "demo_project_maple_ridge_townhomes";
const DEMO_PROPOSAL_SCENARIO_KEY = "proposal";
const DEMO_ACTIVE_SCENARIO_KEY = "active";
```

Project display values:

```ts
projectName = "Maple Ridge Townhomes"
projectSubtitle = "Phase 1 reimbursement proposal · Hamilton, ON · reimbursement only"
```

### 20.3 Seed Dates

Use fixed dates so Playwright tests are stable.

```ts
const DEMO_PROJECT_START_DATE = "2026-01-05";
const DEMO_TODAY = "2026-05-08";
const DEMO_PAYOFF_DATE = "2027-01-05";
```

Do not use the real current date for seeded plan math. Use `DEMO_TODAY` inside seed and tests. UI may label it as `Today`.

### 20.4 Money and Date Representation

Use integer cents for money.

```ts
8400000 // $84,000.00
```

Use ISO `YYYY-MM-DD` strings for date-only fields.

Use milliseconds timestamps for audit/event creation fields where Convex convention makes that easier:

```ts
createdAt: number
updatedAt: number
```

Do not use floating dollar values in persisted state.

Interest calculations may produce fractional cents internally, but persisted displayed estimates should be rounded to nearest cent.

Create a shared demo domain module, for example:

```txt

```

It should export these enums/types or equivalent literal unions.


Reset semantics:

- `all` clears and reseeds both Proposal and Active scenarios.
- `proposal` clears and reseeds only Proposal.
- `active` clears and reseeds only Active.
- Cleanup must delete all related demo tables for the chosen scenario.
- Reset must be idempotent.

### 20.10 Cost Formula Contract

Use integer cents for displayed/persisted money. Interest computation may use floating point internally and round to cents at the boundary.

```ts
annualRate = annualInterestRateBps / 10_000
interest = requestedDrawAmountCents * ((1 + annualRate / 365) ** daysOutstanding - 1)
interestCents = Math.round(interest)
```

Draw fees:

```ts
drawFeeCents = count(drawGroups where requestedAmountCents > 0) * flatDrawFeeCents
```

Projected borrower cost:

```ts
projectedBorrowerCostCents = approvedProjectValueCents + drawFeeCents + estimatedInterestCents
```

Projected capital actually drawn:

```ts
projectedCapitalDrawnCents = sum(drawGroup.requestedAmountCents)
```

Rollover/unclaimed buffer:

```ts
rolloverBufferCents = approvedProjectValueCents - projectedCapitalDrawnCents
```
