03

Relationship authority

The graph carries two deliberately different classes. A reference can inform; only a domain-owned constraint can gate.

Class A · informational

Reference

Context and navigation only. It cannot change state, satisfy policy, or make a target command eligible or ineligible.

subjectPrimary entity the content concerns
contextAnother relevant entity
sourceImmutable origin or provenance
supporting_recordMaterial supplied without a sufficiency claim
Never: generic blocks, proves, or affects edges.
Class B · operational

Domain-owned constraint

May affect a command, but only its authoritative domain can create, evaluate, satisfy, waive, or retire it.

  • Action Item dependency gates Action Item completion
  • Draw requirement gates a Draw command
  • Evidence requirement owns sufficiency and waiver
  • Site Visit requirement owns inspection state
  • Every policy decision emits domain audit
Rule: the relationship stores the edge; the owning domain stores policy state and evaluates the gate.

05

Cutover without parallel truth

Compatibility is a temporary read contract. It is never an excuse for two indefinite writers.

Inventory + classify

Map every legacy link, dependency, primary reference, and projection to informational, constraint, derived, or invalid.

Idempotent backfill

Create canonical edges tenant-by-tenant. Preserve organization, Build, actor, timestamps, and publication provenance.

Prove parity

Compare edge counts, subjects, dependency DAGs, ACL visibility, audit identity, and projection output.

Single-writer cutover

Move writes to the successor once. Serve legacy read contracts only from derived compatibility projections.

Retire overlap

Remove legacy writes and redundant storage after observation. Quarantine ambiguous records instead of guessing.

06

Next pattern · Fieldwire

One field-work object can coordinate many kinds of work without becoming the system of record for every workflow it touches.

Decision awaiting confirmation

Should Action Item be DrawFlow’s single coordination envelope for field questions, missing information, inspection follow-up, progress concerns, delays, punch work, and document requests?

One coordination envelope

Use Action Item across field collaboration use cases. Tags, typed references, and supporting records provide context; an explicit domain command creates any real operational requirement.

Specialized collaboration objects

Create separate Issue, RFI, Punch Item, Document Request, and Field Follow-up records. Vocabulary is precise, but workflows, activity, ACL, and references begin to compete.

Action Item owns operations

Make one universal Action Item absorb evidence sufficiency, inspection state, Draw policy gates, and Milestone completion. Simple surface, incorrect authority.

Recommendation: one coordination envelope. A plan/sheet or location is context; a photo, form, or file is a supporting_record; neither proves progress. When the concern needs operational force, an authorized domain command accepts it, creates a domain-owned requirement, and retains the Action Item as source provenance.
